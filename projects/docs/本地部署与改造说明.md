## 三、本次改造：原数据库设计的问题与修复

### 3.1 原设计的四个硬伤

| 级别 | 问题 | 后果 |
|------|------|------|
| P0 | **前端 `AppState` 被当成唯一数据源**，每次保存把整个状态覆盖写库，并「删除数据库里多出来的行」 | 只要某次请求带的数据不完整，就会**误删别人的数据**；本质是数据丢失 |
| P0 | **接口完全无鉴权**，服务端用高权限密钥直连数据库；`GET /api/state` 还会把**明文密码**下发给前端 | 一条 `curl` 即可读走全部数据甚至清库 |
| P0 | **密码明文存库**（`dealers`/`stores`/`employees`/`persons` 四张表各有一个 `password` 列），且在浏览器里比对，还有 `admin/123456` 硬编码后门 | 任何能读库/改前端的人都能登录任意账号 |
| P1 | **过度使用 JSONB**：水位、状态、关联 id 数组、字段定义全塞 jsonb | 这些值在 SQL 层无法过滤/比较/统计，只能在浏览器里遍历，数据量一大就崩 |

### 3.2 修复后的架构

**① 数据库：真正的表结构（31 张表）**

- 拆出 `accounts` / `sessions` 统一承载登录凭据与会话，业务表不再存密码。
- `alerts` 的关联 id 数组拆成 `alert_task_stores` / `alert_task_dealers` 真表，可按店仓/经销商直接查。
- 同步水位 `value_num` / `value_text` 抽成真列，可在 SQL 里比较。
- 旧版 8 张结构完全相同的 `sync_*` 表合并为 `sync_resources`（用 `type` 区分）。
- 只有**文档型数据**才用 jsonb：画布 `nodes/edges`、字段定义、预览行、权限 pages。
- 补齐：主键、**29 个外键**、**176 个 CHECK**（枚举取值的硬约束）、`updated_at` 触发器。
- 迁移框架 `db/migrations/*.sql` + `schema_migrations` 版本表，DDL 不再靠代码 `ensureSchema()` 临时拼。

**② 写入：增量 upsert + 软删除 + 显式删除通道**

- 保存只做 upsert，**绝不按入参删除**；删除必须通过 `del` 字段显式声明目标 id。
  彻底消除「空数组 = 清库」。
- 业务表删除一律软删除（`deleted_at`），配合部分唯一索引，历史可追溯。
- 关键动作写 `audit_log`（登录、登录失败、改密、删除、清空告警）——旧版完全没有留痕。

**③ 鉴权：认证 + 授权都在服务端**

- 认证：scrypt 加盐哈希存库；会话为 httpOnly + SameSite=Lax Cookie，库里只存 token 的 SHA-256；
  12 小时过期、连续失败 8 次锁定 10 分钟；中间件作为网关，未登录的 `/api/*` 一律 401。
- 授权：接口按数据库里的角色配置重新计算权限（与前端 `perm.ts` 同一套语义）。
  修复了旧版「改一下 localStorage 的显示名就能变成别人」以及「配了权限也拦不住直接调接口」。
- 同步平台的 `x-user` 请求头不再被信任（旧版可任意伪造审计身份），改为服务端解析出的账号。

**④ 前端：不再把本地缓存当真相**

- 会话失效（401）不再静默回退 localStorage，而是清标记并跳登录页——
  否则界面看着能用、其实写不进库，最容易误判成「数据丢了」。
- 本地缓存按**账号 id 隔离**，多人共用一台电脑不会串数据。
- 「退出系统」现在会真正调用 `/api/auth/logout` 销毁服务端会话（旧版只清了显示名）。

## 四、常用运维命令

```bash
pnpm db:status      # 查看已应用的迁移
pnpm db:migrate     # 应用新迁移
pnpm db:schema      # 从实际库导出 docs/DB_SCHEMA.md
pnpm test:smoke     # 端到端冒烟（登录/写入/部分提交不丢数据/显式删除/匿名拦截）16 项
pnpm test:authz     # 服务端授权（越权写入返回 403、防提权、角色移除）17 项
pnpm ts-check       # TypeScript 类型检查
```

备份与恢复：

```bash
# 备份
pg_dump -h 127.0.0.1 -U warn_app -d warn_platform -Fc -f backup_$(date +%F).dump
# 恢复
pg_restore -h 127.0.0.1 -U warn_app -d warn_platform --clean backup_2026-09-22.dump
```

重置（**会清空所有业务数据**）：

```bash
pnpm db:reset && pnpm db:setup
```

> PostgreSQL 开机自启：`brew services start postgresql@16`。
> 若该命令报 `Bootstrap failed: 5`（launchctl 受限环境常见），
> 用 `pg_ctl -D /opt/homebrew/var/postgresql@16 start` 手动启动，
> 或者直接用 `scripts/local-start.sh`（会自动拉起）。

## 五、已知限制与后续建议

1. **数据范围（行级）过滤尚未在服务端强制。**
   角色里的 `data_scope`（自己/本经销商/本店仓/自定义）目前只作用于界面展示。
   一个已登录的低权限账号调 `GET /api/state` 仍能拿到全量数据。
   要真正隔离，需要按实体在 SQL 层加范围条件（告警按店仓、数据表按分组等），
   工作量较大，建议作为下一阶段专项。

2. **权限语义保留「未配置角色 = 全开」的开箱即用兜底。**
   即：某账号若没有命中任何角色模板，则不受限制。
   这是为了让系统开箱可用、不破坏原有行为。若要收紧，可在
   `src/lib/server/authz.ts` 里把 `matched === false` 由「放行」改为「仅只读」。

3. **同步平台的 `sync_resources.data` 仍是 jsonb**（各类资源字段差异大，属文档型数据）。
   `name`/`status` 已抽成真列，常见的列表检索与统计不受影响。

4. **`src/components/sync/**` 与 `src/lib/server/sync/**` 存在历史 lint 告警**
   （`no-explicit-any`、`prefer-const` 等，共 118 处），不影响构建与运行，
   新的接口层与鉴权代码均已通过 lint。
