# 项目上下文

## 项目概述

预警规则画布：可视化编排预警规则（节点流 + 求值引擎），规则触发后产生预警工单，数据经 Supabase 持久化。前端读写整份对象（DataTable / AlertRule / AlertTask），经 `/api/state` 全量读取与全量覆盖式同步。

### 预警/规则/分组模型关联

- **预警工单** `AlertTask`：字段含 `id`(NOT NULL，落库必需，缺失时后端 `syncAlerts` 自动补齐)、`ruleId`、`ruleName`(规则标题)、`title`(预警标题)、`level`、`status`、`dept`、`assignee`、`preview`、`conditionDesc`；**处理流程新增字段**：`acceptedAt?`(接受时间)、`startedAt?`(开始处理时间，此时才开始计时)、`handledAt?`(完成/无法完成时间)、`resolution?`(完成时必填的处理方案)、`failedReason?`(无法完成时必填的原因)、`comments?: AlertComment[]`(`{id,by,text,at}` 沟通记录全家桶)。DB `alert_tasks` 已加对应列（`accepted_at/started_at/handled_at/resolution/failed_reason` 为 nullable，`comments` jsonb），`repo.ts` 的 `AlertRow/toAlertRow/toAlertTask` 均已映射，经 `/api/state` 全量同步持久化。
  - **预警状态机（二次确认 + 计时）**：`new → processing(开始处理) → done(完成) / failed(无法完成)`（**已删除「接受」环节**，直接从开始处理开始；类型保留 `accepted` 仅兼容历史遗留脏数据，其按钮配色判定把 `accepted` 归入可开始处理可操作）。每次操作都经 `openConfirm` 二次确认弹窗，完成/无法完成**必填文本**（处理方案/原因）否则确认按钮禁用。开始处理=正式计时(`startedAt`)并成为处理人(`assignee=who`，`who` 由调用处传 `meName`)；完成=`done`+`resolution`；无法完成=`failed`+`failedReason`。转交独立弹窗（`handoffId`→`processing`+`handoffTo`+换 `assignee`）。时长：`formatDur(startedAt, handledAt ?? now)`，列表「处理耗时」列与弹窗元信息实时显示（`processing` 中按每秒 `now` 计时，紫色高亮）。处理方案/无法完成原因在弹窗正文底部以卡片记录展示。`buildActions`（AlertList.tsx）签名 `(a, update, handoff, ask, who='当前用户')`，`ask=openConfirm`。操作按钮渲染在**弹窗头部标题之后**，**四个按钮常显展开**（开始处理/完成/转交/无法完成，已删「接受」）；按钮样式按“已完成/不可用 → 灰色（`cursor-default` 空操作）、未完成且可操作 → 蓝色”配色（转交为描边浅色）。可操作性判定：开始处理=新(含遗留 accepted)、完成=处理中、无法完成=新/处理中、转交=无法完成同。**注意 buildActions 目前是模块级独立函数**（不在组件闭包内，用闭包捕获 `now` 时已验证组件内 `now` 为 Date.now 数字）。
  - **查看弹窗为全屏**（`fixed inset-0 flex flex-col bg-white`，无深色遮罩、靠右下 X 关闭），正文两区：左＝可选「历史预警」侧栏（`showHist` 状态控制显隐）、右＝详情（头/元信息/正文/操作页脚）。**历史预警归并键 `historyKeyOf(a)`** = `ruleId||ruleName::preview.storeMessages[0].store`（同一规则+同一触发主体=店仓/款色等「store 列首值」视为同类）；点历史条目 `setOpenId(h.id)` 直接切换到该预警并自动重算同类列表。列表头右上「历史预警」按钮切换侧栏，带同类数量徽标。
  - **预警处理方式**：数据表下方、留言上方为「预警处理方式」文本框（`planDraft` state，持久化字段 `plan`，DB 列 `alert_tasks.plan`），灰色占位文案；`onBlur` 时若变化则 `updateAlertStatus(id,{plan})` 写库。非必填、随时可改。
  - **留言**：处理方式下方为留言区（`comments` 复用），所有看到该预警的人均可留言（不做权限区分）；`chatDraft` + `sendMsg`(追加 `{id,by,text,at}` 到 `comments` 经 `updateAlertStatus` 持久化)。每条留言展示发送人信息：姓名 + **部门**（`persons[by].orgId → orgs[].name`）+ **职位**(`title`) + **岗位**(`post`) + 时间（`personMeta` 解析）。支持**回复**：`replyTarget`/`replyDraft` + `sendReply(cid)` 把回复写入该留言的 `replies`（AlertComment 新增 `replies?: {id,by,text,at}[]`，jsonb 无需改表，repo 内联类型已同步）。**撤回/删除规则**：本人留言/回复在 **1 小时**内（`now - at <= 3600000`）可「撤回」；超过 1 小时或非本人，仅**管理员**（`canView(perm,'perms')` 判定 `isManager`）可「删除」；两者都经 `delComment`/`delReply`（内部二次确认）删除对应 `comments`/`replies` 条目并 `updateAlertStatus` 写库。持久化链路：`updateAlertStatus` → reducer UPDATE_ALERT → `useEffect[state]` 写 localStorage + 600ms 防抖 `pushRemoteState(/api/state)` → repo sync 落库，`plan`/`comments` 均走此通道。`isManager` 在组件内 `canView(resolvePerm(me,state.config),'perms')` 计算。弹窗为单列布局，右侧无聊天窗口；曾在右侧做过「沟通聊天+在线状态」，已按要求取消（在线状态相关 presence 表/API/repo 函数已全部移除，DB `presence` 表已 drop）。
- **预警标题规则**：`buildAlertsForRule`（`src/lib/store.tsx`）生成预警时，`title` **一律等于该动作节点的 `title` 字段**（`ActionNodeData.title` 的 `.trim()`，即动作面板「预警标题」输入框），未填时回退规则标题 `rule.name`。⚠️ 曾给 title 追加 ` · ${store}` 店仓后缀（`mk` 里 `storeMsg` 拼接），已按用户要求**移除**——现在 title 就是动作标题纯值，不随 store mode 变化；store 信息改从 `preview.storeMessages` / 接收人(assignee) 体现。`ruleName` 始终为规则标题，与 `title` 可不同。动作节点面板已有"预警标题"输入框（带"将显示在预警列表的标题列"提示）。
- **预警分组**：`AlertRule.groupId` 关联 `RuleGroup`(id/name/created_at)。前端 `AlertList` 经 `ruleId → rule.groupId → ruleGroups.name` 解析分组名展示；无 → '—'。分组数据经 `/api/state` 同步。
- **预警按商品/店仓维度筛选（新增）**：`AlertTask.dims?: AlertDims`（`AlertProductDims{brand/year/season/category/style}` + `AlertStoreDims{brand/company/department/salesArea/district}`），`buildAlertsForRule` 生成预警时经 `computeAlertDims(a, stores)` 写入。**商品维列名按中文别名匹配预览行**（品牌/品牌名/brand、年份/year/年、季节/season、品类/类别/category/大类、款色/款号/style/SKU），数据表无对应列则该维缺省、不在筛选下拉出现；**店仓维取整于命中店仓的门店档案**，字段取值**同时兼容顶层字段与 `attrs` 字典键**（`主营品牌`/`品牌`、`所属分公司`/`分公司`、`所属部门`/`部门`、`销售区域`、`区部`）——实测门店档案维全在 `attrs` 键 主营品牌/分公司/部门/销售区域/区部（顶层空）。`AlertList` 筛选栏下新增「按商品」（品牌/年份/季节/品类/款色）+「按店仓」（主营品牌/分公司/部门/销售区域/区部）两排下拉，**选项从已有(可见)预警统计去重**（`dimOptions` useMemo，无该维数据的预警不产生选项），与现有 kw/等级/状态/时间筛选叠加（AND）；**旧预警无 `dims` 时前端 `enriched` useMemo 实时 `computeAlertDims` 补算**（不强制重存），故历史 store 模式预警（含 storeIds 空、仅 storeMessages 有店仓名）也能按店仓/商品筛选。重置按钮 `emptyFilter` 已含全部维 key（`setFilter(emptyFilter)` 一键清空）。
- **按店仓模式激活后"预警列表为空"诊断结论（重要）**：`buildAlertsForRule` store 拆分为每命中店仓一条是正常的——实测规则「零售排名第一款色-未售预警」(active) 已生成 24 条 store 模式预警落库（`/api/state` 可见，每条 `storeMessages` 单店仓，店仓名 21/24 能精确匹配 `stores[].name`）。**若列表仍看不到，根因基本是数据权限过滤**：`AlertList` 的 `alerts = filterAlertsByScope(state.alerts, scopePerson??me, perm.dataScope, state.stores)`；store 模式预警归属到具体店仓（`storeIds`，旧预警回退 `storeMessages[].store` 映射 id），当**当前登录账号的数据权限**（all→全见 / dealer→仅下级经销商 / store→仅本店 / managed/custom→指定集合 / self→**仅本人 assignee**）不含这些店仓即整批隐藏。用 `inferScope` 推断：无 `dealerId/storeId` 的管理员会落到 `self`（自看），看不到他人的店仓预警。排查顺序：先 `curl /api/state` 看 `alerts` 是否真有数据（有→权限/登录账号问题，无→生成/求值问题）；再确认 `localStorage.dn_auth` 账号与其数据权限。⚠️ 旧预警 `storeIds` 为空是历史数据（改动写入 `storeIds` 之前生成），非 bug；新激活的会带 `storeIds` + `dims`。
- **预警列表列结构（当前版）**（`src/components/AlertList.tsx`）：按序为 预警标题(`title`) / 重要程度(`level`) / 预警分组(`groupOf`) / 条数(=`preview.storeMessages` 或 `rows` 条数) / 预警规则(`ruleName`) / 接收人(`assignee`/`handoffTo`) / 已过时间(`ElapsedCell`) / **处理耗时**(`formatDur(startedAt,handledAt??now)`，未开始显示 —，processing 中显示实时时长并紫色高亮) / 状态 / 操作（仅「查看」）。**「生成预警」按钮及整个人工建预警功能已删除**（移除 `creating`/`createAlert`/`ruleId`/`level`/`title`/`content`/`reason` 状态与对应弹窗，及 `addAlert` 解构、`Plus` 图标导入）；**快捷日期按钮（今天…全部）已并入筛选搜索栏为同一行**（`flex-wrap`）。已删除列：序号、创建人(`createdBy`)、创建时间(`createdAt`)、「适用部门」(`dept` 字段仍保留)、「适用店仓/适用员工/适用用户」（三列曾取 `preview.recipients` 中 `mode==='store'/'employee'/'person'` 的 `names`，现整列与对应筛选下拉、`recipientNames`/`alertStores` helper、 `storeOptions/employeeOptions/userOptions` 均已移除）。“接收人”列原为「适用人员」。列表上方有「快捷日期标签（今天/昨天/本周/上周/本月/上月/全部，经 `quickRange` 生成 start/end 驱动 `filter.start/end`）+ 自定义日期区间 + 四项统计卡片（预警条数=总数、已完成=`done`、未完成=总数-完成-失败、无法完成=`failed`）」，统计基于当前筛选结果 `filtered` 动态计算，与列表同步联动。
- **预警动作独立开关**：动作节点数据含 `enabled?: boolean`，`buildAlertsForRule` 过滤 `enabled !== false`；配置页激活与列表页启用（`activateRule`）均会生成本规则预警。
- **`ADD_ALERT` 派发 payload 契约**（曾踩坑）：store 的 `addAlert` API 与 reducer `ADD_ALERT` 都以**预警对象本身**为 payload（`dispatch('ADD_ALERT', alert)`），reducer 第一行 `isBlankAlert(action.payload)` 直接判 title/ruleName。**严禁在 API 层把 alert 再包一层 `{alert}`**——那会让 reducer 拿到 `{alert:...}`，title/ruleName 为空被判为空白预警而静默丢弃。症状：配置页保存并激活规则时 status 变 active、提示"已激活"，但预警列表始终 0 条（而列表页「启用」走 `activateRule` 的 `dispatch('ADD_ALERT', a)` 正常落库），造成"同一条规则有的端能出预警、有的端始终不出"的假象。改派发形式时务必保持两处（`addAlert` 与 `activateRule`）一致。⚠️ **`activateRule` 合并已存在预警时严禁整包覆盖**：之前 `UPDATE_ALERT patch: {...a}` 会把重新构建的全新 `status='new'` 覆盖掉用户已产生的处理状态与内容（status/resolution/failedReason/comments/plan/acceptedAt/startedAt/handledAt/assignee），表现为"处理好的预警又全变待处理"。现在已改为解构剔除这些运营字段(`_s/_as/_ac/_sa/_ha/_rs/_fr/_cm/_pl`)，只 `...fresh` 刷新可再生数据。
- **全量覆盖同步风险**：`/api/state` POST 会全量覆盖数据库（upsert 传入 + 删除不在传入集合的旧预警）。`syncAlerts`（`src/lib/server/repo.ts`）已加**空集合守卫**：本次提交 alerts 为空数组时不执行 stale 删除（return），避免前端某次空同步误删全部业务预警。任何调整预警同步逻辑或新增前端触发源时，务必注意"若某次 push 的 alerts 集合不完整，会静默删掉库中其它预警"。
- **组织架构 / 人事架构**：承载预警通知对象（最终通知到"用户和人员"）。组织 `Organization`（表 `organizations`：`id/name/kind/parent_id/sort/created_at`）——用户明确"是平级标签"（总部/分公司/部门/区域/门店/其他，`kind` 分类，`parentId` 预留但默认不同）。人员 `Person`（表 `persons`：`id/name/org_id/title/post/supervisor_id/manage_scope(JSONB)/phone/email/enabled/sort/created_at`，`title`=职位、`post`=岗位，均来自「职位/岗位管理」属性标签），**挂在组织节点下**（`orgId`）；`manageScope` 用 `ManageScope{tableId,field,value,desc}` 表达"管理范围＝某数据表某字段=某分类值"（如 该店长管理"大区=华东大区"下的门店/人员）。`supervisorId` 为上级人员（空=最高层）。经 `/api/state` 的 `orgs`/`persons` 全量同步（repo `getAllOrgs/syncOrgs/getAllPersons/syncPersons`）。页面：`PeopleManage.tsx`（人员管理：部门树+人员增删改；部门「编辑」复用 `OrgModal` 弹窗，可改名称/上级部门/分类）、`AttrManage.tsx`（属性管理：属性+子标签，接受 `category` prop 按分类过滤）。挂载于 `page.tsx` 的 `View='people'/'attrs'`（导航「人事管理」父级下展开 人员管理/属性管理）。⚠️ 曾有的「组织属性」（`AttrManage category="org"`，`View='org'`，导航「组织架构」首子项）已按用户要求**彻底删除**（含页面与数据库 `hr_attributes.category='org'` 记录）；`page.tsx` 已无 `'org'` 分支，`AttrCategory` 不含 `'org'`，store 加载时过滤 `category='org'` 残留（`(a.category ?? 'person') !== ('org' as never)`）避免全量 POST 回写脏数据。通知动作面板（`nodes.tsx` TargetPanel）通知对象已改为从 `state.persons`/`state.organizations` 动态选择（`notify.orgIds`/`personIds`），不再用写死常量 `PERSONNEL`/`DEPARTMENTS`（import 已移除）。
  - **人事架构为分层树**：总部 `org_head` 为根，其下通过 `parent_id` 挂总经办 `org_zjb` 及人事部/团购部/电商部/商品部/督导部/仓储部/财务部/企划部/全国部等部门（seed）。`PeopleManage.tsx` 左侧按 `parentId` 递归渲染部门树，部门卡片支持上级组织选择、上移/下移（store `moveOrg(id,dir)`）与编辑/删除。

## 规则引擎节点（预警规则画布）

- 求值引擎：`src/lib/evaluate.ts` 的 `evaluateFlow(nodes, edges, tables)`，按 `flow.nodes` 数组顺序逐节点求值（无连线时依赖数组顺序），结果写入 `outputs[nodeId]`。
- **节点数组顺序即执行顺序**：新增上游节点（如过滤/聚合）时，必须把它排在引用它的下游节点之前，否则下游 `byId(nodeId)` 取不到结果会 fallback 到错误节点。
- **求值用引用依赖补齐拓扑**：`evaluateFlow` 的拓扑排序默认只认连线（edges）。若某节点通过 data 显式引用上游（`factNode`/`sourceNode`/`universeNodeId`/`left`/`right`/`ref`），则 `collectNodeDataRefs(node)` 会把该引用也算入依赖，确保上游先求值；无引用时仍依赖数组顺序。故这些"引用型"节点（如 filljoin 关联的结果节点）可不必画线，引擎会自动等待上游就绪。
- **filljoin 匹配键去重**：输出列生成时会对匹配键（主键 + extraKeys 的全集侧）去重，同一全集键只输出一次，避免重复列。
- **添加列（calc）节点**：选择数据表（`source:'table'`+`tableId`）或上游节点结果（`source:'node'`+`sourceNode`），rowset 统一用 `resolveRowset({tableId,source,sourceNode})` 解析（返回 `{t,from}`，`t` 为真实表或虚拟表）。对每行按 `columns[].expr` 用 `evalCalcString` 逐行求值追加新列。**表达式引擎**（evaluate.ts 顶部 `CalcParser` 递归下降）：字段用 `[字段名]`，支持字符串`'…'`/数字/布尔，运算符 `+ - * / % &`、比较 `= == != <> > >= < <=`、逻辑 `AND OR NOT`、括号；函数 `IF(条件,真,假)/CONCAT/NUMBER/TEXT/SUBSTR(文本,起始[,长])/LEFT/RIGHT/LEN/YEAR/MONTH/DAY/DATE(年,月,日)/TODAY()/NOW()/DATEDIFF(A,B)`（返回 A-B 天数，日期用 `YYYY-MM-DD`）。同一节点内后一列可引用前一计算列（逐列顺序求值，`o[c.label]` 已入 row）。布尔结果输出为 `是/否`，null 输出 `''`。⚠️ `collectNodeDataRefs` 已收集 `sourceNode`，无需画线即自动拓扑依赖。注册接线点：types `NodeKind/CalcNodeData/KIND_LABEL/KIND_COLOR`、evaluate `case 'calc'`、nodes.tsx `inferNodeCols('calc')/getNodeOutputs('calc')/CalcNode 面板/calc:CalcNode`、FlowCanvas 面板 `flowItems` 与 `NODE_GROUPS`（计算与统计）。新增函数只改 `calcCall` 与面板 hint。
  - **添加列公式框（CalcExprEditor.tsx）**：基于 **contentEditable** 的公式编辑器——用 div.innerHTML 把公式按 `[字段名]` 解析 `parseSegs` 后重建 DOM：普通文本为文本节点（可任意点击/方向键定位光标）、字段为 `contentEditable=false` 的蓝色标签 span（`data-field`），带 ✕ 按钮一次删除整个字段、退格键也可整体删除。序列化 `serialize` 遍历子节点：文本节点取 `textContent`、`data-field` span 还原为 `[字段]`，得到公式串经 `onChange` 写 `columns[].expr`。对外 forwardRef handle：`insertField(name)`（光标处插入字段标签，用 Range `insertNode`+`setStartAfter`）、`insertText(text, caret)`（插入普通文本，caret 为文本内光标偏移——函数模板由 `insFn` 按 `tag.indexOf('(')+1` 计算光标落在参数位）。⚠️ 光标稳定性：DOM 由非受控方式手动维护，仅当外部 `value !== lastRef.current`（切换节点等）时才重建，正常输入/插入后 `lastRef` 同步为序列化结果，故 React 重渲染不会重置光标。⚠️ 函数模板占位（`CALC_FNS` 的 `tag`）用**无方括号**的 `日期A/条件`，避免被 `parseSegs` 误当字段；真实字段只能通过面板字段按钮 `insertField` 插入。⚠️ contentEditable 容器不得用 flex 布局（影响光标定位），用普通 block + 内联节点。曾踩坑：受控 `value` input 会重置光标，务必非受控。
- **计算节点可链式引用前一计算**：compute 用"两节点结果运算"（`expr.leftType='node'`）时，`expr.left.nodeId` 指向被引用节点，evaluate 用 `byId(nodeId)` 取其完整输出，`tokens` 里选该节点结果列（如第一个计算的 resultLabel"连带率"）做二次运算。`collectNodeDataRefs` 已收集 `left.nodeId`，故自动建立拓扑依赖，无需画线。⚠️ **同一节点内两字段逐行运算（如 `已过天数 － 开单天数`）**：UI 把算子数值填在 `expr.left.col` 与 `expr.ref.col`（两列指向**同一个** `nodeId`），`tokens` 为空栈。`collectNodeDataRefs` **必须同时收集 `d.expr.left.nodeId` / `d.expr.ref.nodeId`**（旧代码只收集顶层 `d.left/right/ref`，漏了 `d.expr.*`，导致 compute 不依赖任何上游 → 排在 filljoin 之前求值 → `byId` 取不到上游表 → 误走成标量分支返回空）。修复后 compute 正确命中 line ~1799 的 `sameNode` 分支逐行算两列。⚠️ 若再改 `expr` 结构或新增 compute 子模式，务必确认 `collectNodeDataRefs` 覆盖所有上游 nodeId 引用（否则无连线规则的拓扑会乱序导致预览为空）。
- **引用下拉（refOutputs）对同一节点去重**：`getNodeOutputs` 会给 compute 同时注册 `column` 和 `scalar` 两条同名记录（label 都是 resultLabel），若不按 nodeId 去重，下拉/列表里同一计算节点会重复显示（如两个"连带率"），极易误导为"计算组件重复"。
- **compute 的 inferNodeCols 递归带出上游字段**：`inferNodeCols` 对 compute 在"两节点结果运算"（`expr.leftType='node'`）时，会沿 `expr.left.nodeId` 递归取上游节点的全部输出列 + 追加自身结果列，供"点字段加入"候选；否则仅返回自身 resultLabel 一列。带 visited 集合防环（节点自引用即截断）。改动时注意保持该行为，否则选了数据节点后"点字段"里只有结果列、看不到上游分组的具体字段。
- **排名（rank）可链式叠加**：rank 节点输出列 = 上游全部列（baseCols 透传）+ 每个排名项「排名」「TOP档」两列。因此第二个 rank 若引用第一个 rank 节点，预览会同时带出第一个 rank 的全部列（含其"折扣排名"）并在其上追加"连带率排名"，实现"在上一排名基础上增加一列排名"。⚠️ 要达到此效果，第二个 rank 的"引用节点输出"必须选**第一个 rank 节点本身**，而不是各自引用 compute（那样拿不到上游排名列）。
- **rank/TOP 列名去重**：排名列与 TOP 档列生成时统一用 `uniq()` 避开 baseCols（上游透传列）与已用列名，冲突时追加 `#2/#3`，避免链式 rank 复用同字段时 TOP 列覆盖（旧实现只对 items 内同名去重，感知不到上游透传列）。

- 诊断脚本可用 `npx esbuild /tmp/x.ts --bundle --platform=node --format=esm --outfile=/tmp/x.mjs` 打包后 `node /tmp/x.mjs` 运行。
- **数据表删除保护 + 规则删除/复制的二次确认**：用户不允许"删数据表连带删规则"。store `REMOVE_TABLE` 已改为：若有规则 `r.tableIds?.includes(id)`，**直接拒绝删除返回原 state**（不再隐式清掉引用规则）；未引用时只删表、不动规则。UI 两层配合（DataTableManager.tsx）：删除按钮先 `tryDelete(t)` 计算引用规则 → 弹 `ui/alert-dialog`；被引用时对话框只显示"无法删除 + 引用的规则名"，仅提供「知道了」，无确认删除按钮；无引用时提供「取消 / 确认删除」二次确认。规则侧 RuleList.tsx 的删除与复制也走同一个 alert-dialog 做二次确认（copy 确认文案注明"复制后为草稿"）。⚠️ 改 REMOVE_TABLE 时勿恢复旧逻辑（删表时 `rules.filter(不含该表)`），否则又会造成"删表丢规则"。引用关系判断一律用 `r.tableIds?.includes(id)`。

- **预警列表字段为空 / 预警无法关联规则**：预警由入驻前端 `buildAlertsForRule`（store.tsx）在「激活规则/手动触发」时生成，会带全字段（ruleId/ruleName/title/conditionDesc/dept/assignee/preview）。若库里出现 `rule_id` 为空、字段全空的碎片预警，说明它不是该路径生成，直接清理。数据库无正确预警时，可用 esbuild 打包的 Node 脚本复用 `evaluateFlow`（读 `alert_rules`/`data_tables` 的 `data` 列 → 对 active 规则求值 → 按 `buildAlertsForRule` 同款逻辑构造 AlertTask → 清空 `alert_tasks` 后 `insert`），`preview` 存 `{columns, rows}`（rows 取前 200），content 用 `{field}` 按首行替换真实列值。注意库同步是前端 `/api/state` 全量覆盖，写库后前端刷新即看到。
- **预警动作（action）节点有独立开关 `enabled`**：`ActionNodeData.enabled?: boolean`（默认开启）。UI 在 action 面板顶部（名输入下方）以开关切换，`buildAlertsForRule`（store.tsx）生成时 `filter(a => a.enabled !== false)`，关闭的动作不生成预警。列表页/详情页"启用"规则走 store 新增的 `activateRule(ruleId)`（内部读 state.tables 调 `buildAlertsForRule` 后逐条 dispatch ADD_ALERT，再置 status=active），使**列表页启用也能生成预警**（不只配置页"激活规则"按钮）。⚠️ 若改动作开关语义，务必同步这三点：面板 UI、buildAlertsForRule 的过滤、activateRule/激活链路，否则会出现"配置了预警但列表没有"。
- **`alert_tasks.id` 为 NOT NULL，后端 `syncAlerts` 必须补 id**：前端 reducer（ADD_ALERT）会补 `id`，但**从 Node 脚本/后端路径注入或部分链路直接落库的 AlertTask 可能缺 id**，直接 `upsert` 会因空主键整批报错、该规则所有预警都写不进去（表现为"激活了但预警列表空"）。修复：`repo.ts syncAlerts` 里 `upsert(rows.map(a => ({ ...a, id: a.id ?? gen() })))`。❌ 前端生成的预警对象（buildAlertsForRule 返回）本来就无 id，靠 reducer 补——脚本复算时必须显式生成 id，勿复用无 id 的原生对象直接落库。

- **画布连线样式**：边固定用 `type: 'bezier'`（贝塞尔曲线，`defaultEdgeOptions` 与 `toRfEdges` 同步）。用曲线而非 `smoothstep`——平滑过渡可避免直角折线带来的"尾部先向右折、再直角跳回左侧 target handle"的观感（用户报连线时尾端跳动）。连线层级用 `globals.css` 的 `.react-flow__edges{z-index:3}` / `.react-flow__nodes{z-index:2}` 让连线盖在重叠节点之上（bezier 边 svg 自身 pointer-events 透传，不挡节点拖拽/点击；Controls/MiniMap 仍默认 5 层在上）。改边类型/z-index 时这两处要保持一致。
- **判断方式文案 `buildConditionDesc`**（store.tsx）：预警"判断方式"列读它。判断节点把条件存 **`conditions[]` 数组**（`conditions[i].op/col/colKind/refNode/{label,nodeId}`，旧顶层 `valueSource/value/refNode` 已弃用），所以 `buildConditionDesc` **必须遍历 `conditions[]`** 拼接"如果 {col} {op 中文} {右值}"。右值优先级：`c.refNode?.label`（选了"平均未开单天数"等节点）＞ `field` 取值字段 label ＞ `between` 的 min~max ＞ 普通值。若仍按旧顶层字段拼，会得到"如果 未开单天数 大于 "（右值空）。

## 数据库（Supabase）

- 凭证由平台注入：`COZE_SUPABASE_URL` / `COZE_SUPABASE_ANON_KEY` / `COZE_SUPABASE_SERVICE_ROLE_KEY`；`supabase-client.ts` 按 dotenv → `coze_workload_identity`（python3，向平台拉取项目环境变量）→ 抛错的顺序加载。
- **运行环境里 shell 不一定预置这些变量**，必须通过 `coze_workload_identity` 取；本地验证 node 侧读取用 `./node_modules/.bin/tsx` 跑 client。
- 业务表（`src/storage/database/shared/schema.ts` 定义）：`data_tables`、`alert_rules`、`alert_tasks`、`rule_groups`（`health_check` 为系统表勿动）。`rule_groups(id,name,created_at)` 存规则分组，`AlertRule.groupId` 引用其 id（`''`=未分组）；经 `/api/state` 的 `groups` 字段全量同步（`getAllRuleGroups`/`syncRuleGroups`，同样 upsert + stale 删除）。
- 表结构迁移/建表：schema 改动用 `coze-coding-ai db upgrade`，或直接对 develop 库 exec_sql；已在线上建好三业务表并 `ENABLE ROW LEVEL SECURITY`。
- RLS：项目无 Auth（场景 A），后端用 service_role_key 天然绕过 RLS，不建 policy（无 policy 时 anon 完全被阻断，更安全）。
- `src/app/api/state`：GET 全量读、POST 全量覆盖同步；字段名 snake_case 与数据库列一致。
- **filter 来源表应从「已有条件字段」反查，勿回退 tables[0]**：过滤节点（filter）若 `data.tableId`/`source` 缺失（用户未持久化来源表），旧逻辑 `resolveRowset` 回退 `tables[0]`、`inferNodeCols` 返回空，导致两个 bug：(1) 来源错取首表（若 tables[0] 是商品表，而条件字段是店仓表字段，则 filter 命中 0）；(2) 下游填 filljoin 全集节点后「全集返回列/匹配字段」无字段可选（用户报"过滤结果命名可用店仓，但全集返回列/匹配字段空"）。修复：evaluate.ts `resolveRowset` 增加按条件字段反查——当 `tableId` 解析不到表时，遍历条件字段用 `t.fields.some(f.key∈fields)` 找到含全部/最多条件字段的表（且返回 `resolvedTableId` 供 filljoin 匹配键拼 `tableId`）；无匹配则回退空（null 安全）。`inferNodeCols` 的 filter 分支同步：无 tableId/source 时用**同一套条件字段反查表**推断输出列，保证 UI 字段候选与 evaluate 一致。⚠️ 维护两个实现时必须保持反查规则一致（evaluate 与 nodes.tsx），否则"有结果但选不到字段"会在 UI 复现。
- **filljoin 缺配事实时，时间窗列仍填当前周期值（勿被 fillValue 覆盖为 0）**：left filljoin 对无单据店仓（事实侧无记录）补缺时，若把「开始日期/结束日期/已过天数/本周天数/本月天数/本年天数」等时间窗列也用 `fillValue` 填成 0/空，会得到"有店仓却无本月起止/已过天数"的错误。这些列是**全局周期常量**（与是否匹配事实无关）。修复：filljoin 补缺分支内，若某行未命中且列名 ∈ `WINDOW_COLS = {开始日期,结束日期,已过天数,本周天数,本季天数,本月天数,本年天数,本日天数,当前日期,周几,第几周,剩余天数}`，改用事实节点 rows[0] 的对应周期值填充（groupby 各组同窗口，取首行安全），其余事实列仍按 `fillValue` 填 0。⚠️ 配套的 inferNodeCols(filljoin) 需保证这些列仍在候选字段里。
